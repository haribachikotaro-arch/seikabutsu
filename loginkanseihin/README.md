# Data Dreamers 認証ポータル

Data Dreamers の既存サイトと同じデザインシステムで構築した、Next.js / React のメンバー認証ポータルです。

## 認証の流れ

1. アカウント作成時に、許可された学校メールと自分で決めたパスワードを入力します。
2. Clerk から学校メールへ届く確認コードを入力し、メール認証を完了します。
3. 初回参加時に、運営から共有された「秘密の暗号」（招待コード）を入力します。
4. 2回目以降のログインでは、学校メール・自分のパスワード・秘密の暗号の3点を確認します。
5. 正しい暗号を入力した一般メンバーには `editor` ロールが付与されます。
6. `admin` は招待コードでは付与されません。Clerk Dashboard またはサーバー側の管理処理で、信頼できる運営メンバーにだけ付与してください。

権限情報は Clerk の `publicMetadata.role` に保存し、ブラウザから直接書き換えられない構成です。招待コードは平文で保存せず、scrypt ハッシュだけを環境変数に保存します。暗号の確認結果は署名済み HttpOnly Cookie としてClerkのセッションIDに結び付けるため、別セッションへの使い回しはできません。

## セットアップ

Node.js 18.17 以上と pnpm が必要です。

```powershell
Copy-Item .env.example .env.local
pnpm install
pnpm invite-code
pnpm dev
```

ローカル確認には `http://localhost:3100` を使用してください。Clerkの開発用認証Cookieを安定して扱うため、`127.0.0.1` では起動・アクセスしないでください。ポートとホストは `pnpm dev` に設定済みです。

`pnpm invite-code` で秘密の暗号を非表示入力すると、次の形式の値が表示されます。

```text
DATADREAMERS_INVITE_CODE_HASH=scrypt\$...\$...
```

この1行を `.env.local` に貼り付けます。入力した暗号そのものは保存されません。

`.env.local` の必須項目:

```dotenv
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...
ALLOWED_EMAIL_DOMAINS=school.example.jp
DATADREAMERS_INVITE_CODE_HASH=scrypt\$...\$...
```

`.env.example` は設定例なので、実際の API キーや暗号ハッシュを貼り付けないでください。

## ロールの設定

招待コード認証に成功した一般メンバーには、自動的に `editor` が設定されます。

管理者を設定する場合は、Clerk Dashboard で対象ユーザーの Public metadata を次のように設定します。

```json
{
  "role": "admin",
  "inviteVerified": true
}
```

編集者に戻す場合は `role` を `editor` に変更します。未知のロールやロール未設定のユーザーは、管理画面へアクセスできません。

## 主な画面

- `/` — 認証の案内
- `/sign-in` — 学校メール・パスワード・秘密の暗号によるログイン
- `/sign-up` — 学校メール・パスワードの登録とメール確認コード認証
- `/join` — 学校メールと秘密の暗号による参加確認
- `/portal` — 認証済みメンバー向け画面
- `/admin` — `admin` 専用画面
- `/setup` — 未設定項目の案内

## 認証エラーと情報漏えい対策

- ログイン失敗の表示は「パスワードまたは秘密の暗号が正しくありません。」に統一し、アカウントの存在、ロック、パスワード・暗号の正否を個別に表示しません。通信失敗も同じ表示です。
- 登録済みメールなどのClerkエラー、エラーコード、SDKの生メッセージを画面へ表示しません。8文字以上・確認用パスワードの不一致など、利用者自身の入力だけに関する案内は残しています。
- アプリの認証APIは失敗時に同じ本文と403を返し、キャッシュを禁止します。試行制限は429とRetry-Afterを維持しますが、認証情報の正否は返しません。
- 招待確認のPOSTは厳密な同一Originを要求します。失敗時は招待Cookieを失効し、ログイン途中に作成したClerkセッションもログアウトを試みます。招待Cookieが正しく検証できない状態ではポータルへアクセスできません。
- 本番の `/setup` は認証済みadminだけが閲覧できます。開発環境の初期設定案内は維持します。

### 必須: Clerk側の登録有無の保護

画面の文言だけでは、ブラウザが直接通信するClerk APIの応答を隠せません。Clerk Dashboardの **Protect → Rules → User enumeration protection → Manage** で **Strict user enumeration protection** を選択し、Saveしてください。アプリのコードからこの設定は変更していません。

公式手順: https://clerk.com/docs/guides/secure/user-enumeration-protection

現在のログインはClerkのパスワード認証とアプリの招待確認を順に行う構成です。画面やアプリAPIは統一していますが、ブラウザ上の通信順序・所要時間・Clerkのセッション作成まで同一になるわけではありません。暗号の確認前にClerkセッションができても、アプリの保護された画面・APIは招待Cookieの検証が終わるまで拒否します。

Strictでは、既存アカウントのメールで新規登録を試みても確認コードではなく本人への通知が送られる場合があります。ログインと新規登録の画面は別のままで、パスワードによるログインを維持します。

### 本番公開前に残る確認

招待コードの試行制限は現在、サーバープロセスのメモリ上にあります。再起動や複数インスタンスで共有されないため、本番では共有ストレージを用いた制限へ移行してください。Clerk側の試行制限・Bot対策、本番HTTPS、管理者権限、秘密情報の管理も別途確認が必要です。この修正はすべての脆弱性が解消されたことを保証するものではありません。

## 検証

### 管理者向け: 登録アカウントを確認する場合

登録情報はClerk Dashboardなどの管理者専用環境で確認します。公開画面へ原因別のエラーやコードを再表示しないでください。

1. メールアドレスの入力を確認します。確認コードの送信だけでは登録は完了しません。
2. Clerk Dashboardで、APIキーを取得したアプリとDevelopment／Production環境を選び、Usersに対象のアカウントがあるか確認します。
3. Clerkのアプリを作り直した場合や接続環境を変更した場合、以前のアカウントは自動では引き継がれません。現在の環境に未登録なら `/sign-up` で登録とメール認証を完了します。以前のアプリを継続する予定なら、そのアプリの正しいキーへ接続先を戻す必要があります。
4. Usersにアカウントがある場合は、メールアドレスとパスワード設定の有無を確認します。秘密の暗号の確認は、Clerkでのメール・パスワード認証に成功した後に実行されます。

公開キーと秘密キーは同じアプリ・環境の組を使用してください。開発用と本番用が混在したキーはアプリ側で未設定として扱います。同じ環境種別でも別アプリのキーの組み合わせは、Dashboardで確認が必要です。

```powershell
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```
